# XSettlers — Dev History

A chronological journal of completed work and resolved decisions, split out of
`docs/TODO.md` (2026-07-30) so that file can stay a pure "what's still left"
list. Organized by the same area headings TODO.md uses. Nothing here is

## Session: first full play-test, and what it changed (2026-07-31)

A single session that started as "add a way to see the neighborhood" and ended
with a game played start to finish, nine commits, and a deployment. Recorded as
one narrative because most of the changes were caused by the play-test rather
than planned, and the causation is the useful part.

* **Neighborhood map built** — `show_sector_neighborhood` had been returning a bare list of known sectors, handed to clients as a Python dict repr. Rebuilt to synthesize the *complete* lattice from center and radius and overlay what's known, so unexplored space is visible as absence — under lazy reveal an unvisited sector has no row to return, and "never seen" is the most actionable thing on a map. Ships changed radius default 2 → 5. `views/render.py` gained `render_map()`, dispatched from `render_status()` on `display.kind == "map"` — on the *shape* of the data, never on which tool produced it. Markdown table rather than ASCII art because every client aligns tables correctly and the target client is a phone; absolute coordinates on both axes so a coordinate read off the map goes straight into `preview_move`. It is a pure view: a test asserts no sector rows, no `player_sectors` rows, and no confidence totals change across a call.
* **Fog decay: proportional → flat, and blink-out** — the old `round(confidence * 0.9)` never reached zero (`round(4 * 0.9) == 4` is a fixed point), so every sector a player had ever seen lingered forever at 4 and every `confidence > 0` filter in the codebase was filtering nothing. Fog never actually forgot. Now a flat subtraction floored at 0, as a single UPDATE: 100 → 80 → 60 → 40 → 20 → 0, gone on the fifth unconfirmed turn. Reverses the earlier ghost-memory design deliberately — five turns of silence should cost you the sector, not leave a stale card on the table. The knob was **renamed** rather than redefined (`CONFIDENCE_DECAY` → `CONFIDENCE_DECAY_PER_TURN`) so an existing `.env` carrying `0.9` fails loudly instead of silently meaning "111 turns to forget". Lives in `db/sectors.py` because `engine/turn.py` imports `sector_tools`, so it can't sit on either without a cycle.
* **Library of games, not one game** — the roster lived in `game_config.yaml` (service-wide) and scenarios supplied `home_sector_by_player`, a parallel list paired by index. Player count was therefore a property of the *deployment*: you could not offer a solo tutorial and a two-player scenario side by side, because picking a scenario didn't pick a roster. Split identity from participation — `game_config.yaml` keeps a player **directory** (one entry per person, one credential), each scenario declares its own **`participants`** (directory email + that player's `home_sector`, optional `is_npc`). `resolve_seats()` pairs them into a `Seat` carrying identity *and* position together, so nothing downstream pairs lists by index — that defect class is gone rather than guarded. `authenticate()` now answers two questions: with no scenario, who are you; with one, may you play *this*. `config/game_solo.yaml` is the 1-player proof, and it plays.
* **`starting_fill`** — bootstrap hardcoded every pod to 100% of capacity, which was both "everyone is too rich" and a subtler distortion: a fleet at capacity cannot accumulate, so production is pure waste and only *consumption* moves the score. Measured at 100% fill, holdings sat at exactly 5400 for four turns while score crept up purely by reshuffling toward goods; the same scenario at 25% grew ~288/turn. Now a scenario field (default 0.3), overridable per pod template so asymmetric starts are a lever rather than an accident.
* **Pods have a `task`; organizations have a `mission`** — one word had meant two things one join apart. Not theoretical: a ship report showed `mission: idle` above a column headed "Task", and the obvious reading was that the pods were idle too. They weren't. Renamed through schema, engine, tools, MCP surface, event types and scenario files, with an `ALTER TABLE RENAME COLUMN` migration that preserves a live game.
* **Named units** — defaults became `S1`…`Sn`/`C1` (a player says "S3", not "Ship-P1-03"), and `rename_organization` lets a player name a unit themselves. Names must be unique within a player's own fleet, case-insensitively: a name is how you issue an order, so an ambiguous one isn't a name.
* **Scanning reworked in three ways.** Range 1 → 2, because a Euclidean radius of 1 reaches only the four orthogonal neighbours (a diagonal is √2) and refusing to scan the sector visibly touching yours reads as broken. **Innate organization sensors** — every ship and colony scans one sector per turn on its own account, identical in every rule to carrying one scan pod. And **relative aiming**: a scan is aimed by an offset from the scanner, addressable as a compass bearing, because sensors are mounted on the thing that carries them and a ship flying away from a sector shouldn't keep seeing it. Two consequences fell out — a scan pattern survives a move with no re-aiming, and range became a permanent property of the aim, so an out-of-range aim is rejected when set instead of failing silently at resolution. A scan reveals only its target; a radius-5 halo was considered and rejected, because if scanning is to cost something it must not also be cheap area coverage.
* **End-of-game scoreboard persisted** — `_calculate_final_scores()` computed the winner, printed it, and returned it to a caller that discarded it. A game whose outcome exists only in stdout is a game nobody can be told they won. Now written as a `game.final_scores` event carrying the full breakdown *and the weights used*, so the scoreboard is self-explaining; `show_game_status` serves the recorded result once the game is over rather than recomputing.
* **Tool responses are JSON** — `call_tool` serialized with `str(result)`, i.e. Python repr with single quotes and `True`/`None`. It survived because every client so far had been an LLM, which reads it fine; anything that *parses* the payload cannot. Blocker for a non-LLM client, and silent — repr looks reasonable in a log.
* **Perimeter auth removed; `/mcp` is open (accepted risk).** The `Authorization: Bearer` gate was incompatible with MCP client connector flows, which take a URL and optionally OAuth but have no field for a static header — a connector could only ever get a 401. Reachability won. Access control now rests entirely on `player_token`, with the roster's placeholder tokens still in a public repo alongside this server's URL, and no rate limiting. Knowingly accepted while the game holds nothing of value; recorded in code at the point of decision (`server.py`'s SECURITY POSTURE comment) rather than only in a changelog, because both of those conditions can change quietly.
* **Deployed and verified** — `xsettlers.fly.dev` running current code, MCP handshake, 19 tools, tool calls round-tripping through `json.loads` at the client end. The shared secret was rotated once before removal, when the deployed value turned out not to match the local `.env`.
* **What the play-test taught, kept in `docs/TODO.md` rather than here** because it is direction, not done: transit stress is currently *rewarded* rather than costly (+15 score/turn in transit vs +3 stationary, because energy scores 0 and burning it frees room for goods); sector *variation* — not scarcity — is what's missing for "find better soil", since depletion already works but every sector starts identical; and the capacity wall arrives around turn 15, after which most production is waste.

## DB & Engine

* **`turn.snapshot` events implemented -- long-standing TODO in `_snapshot_holdings()` finally closed (2026-07-30)** — asked for directly, after a post-game analysis needed a from-scratch replay (an instrumented scratch-DB bootstrap + manual re-execution of the whole game) just to answer "how much did each player waste, turn by turn" -- nothing was ever persisted, `_snapshot_holdings()` only ever printed. Closes the gap `db/events.py`'s own hybrid-payload-strategy docs already promised ("engine `turn.snapshot` events store full state, for replay/disaster recovery") but never actually built. Now writes one `turn.snapshot` event per player per turn (via `_record_event_direct`, same circular-import workaround as `_handle_colonize` -- `db/events.py` imports `get_current_turn` from this module, so `record_event()` can't be called from here), payload carrying after-state holdings, this turn's weighted `score` (identical formula to `show_game_status`/`_calculate_final_scores`), and derived per-resource waste. Waste is *derived*, not separately measured: `wasted = produced - consumed - (after - before)` -- whatever was produced and consumed this turn but didn't show up in the actual holdings delta was lost to a full pod with nowhere to spill (see `_store_org_resource`). `production`/`consumption` are `{player_id: {resource: amount}}` accumulators built inline during work `end_of_turn()` was already doing (`_apply_org_upkeep` and the per-pod loop each gained one line to tally into them) -- **no extra queries added to the hot per-pod loop**, only one before-holdings query (top of step 3) and one after-holdings query (already what `_snapshot_holdings` computed, just factored into new shared `_player_holdings()`). Benchmarked against a bootstrap-scale DB (16 orgs, 96 pods, matching the real game): `end_of_turn()` averages ~20ms including the new writes -- **0.007% of a 300s tick interval** -- so true async/background execution (a task queue, a thread) would be pure over-engineering for this workload; the ledger writes happen synchronously, inline, same as everything else in the turn. New test in `tests/test_turn.py`, hand-verified against a specific saturated-org scenario (worked the exact expected waste/score numbers by hand before asserting them, not just checked "some event got written").
* **Stale bullet, corrected (2026-07-29): consumption deduction is implemented, not deferred.** This bullet predated the pod-storage rework and was never removed once that work landed. Two real consumption paths run every turn from `end_of_turn()`: `_apply_org_upkeep()` (`engine/turn.py:93-114`) charges a flat `ORG_UPKEEP_COST` (5 food + 1 energy) per organization per turn regardless of what it's doing, and each producing pod separately pays `POD_CONSUMPTION_RECIPE` (`engine/production.py:26-32`, e.g. `produce_goods` costs 2 energy + 1 food per pod) drawn from the org's pooled stock via `_drain_org_resource`/`_available_org_resource`, prorated down (not all-or-nothing) if there isn't enough on hand. Confirmed live against the in-progress local game (`xsettlers.db`): every ship reads 100% cargo-full not because nothing is draining, but because production nets positive even after these costs (roughly +13 energy / +11 food / +8 goods per ship per turn at full production) — the real gap is storage capacity vs. production rate, not missing consumption logic.
* **Sector resource depletion implemented (2026-07-29)** — production is now capped by the sector's own remaining resource pool, not just the pod's `storage_capacity`. `engine/production.py`'s new `RESOURCE_CAPACITY_COLUMN` maps each produced resource to its `sectors` column (`energy`→`energy_capacity`, etc.); `engine/turn.py`'s production step looks up the pod's org's current sector, caps the amount produced at `min(flat_rate, sector's remaining capacity)`, and decrements that column (floored at 0, via `MAX(0, col-?)`). No regeneration yet — once a sector's column hits 0, that resource stays unproducible there until something (not yet built) replenishes it. **Exception:** a ship in transit is parked at the sentinel sector (`id=-1`), which has no real resources — transit production stays at the flat, uncapped rate per the pre-existing "pods produce regardless of transit state" rule, unaffected by this change. **Deferred, not built:** cross-player contention — when multiple players' pods share one sector, pods are currently processed in `pod.id` order, so whoever's pod resolves first that turn gets first claim on what's left; no fair-split/priority model exists yet. **Tuning note (2026-07-29, same day):** the initial flat `DEFAULT_SECTOR_RESOURCE_UNITS=20.0` was tested against a real bootstrap and turned out to be far too low — a player's full 8-ship fleet demands 480 energy + 480 food + 240 goods per turn at the shared home sector, so the whole pool drained in a single turn with no regeneration, permanently zeroing that resource there. Bumped to `1000.0` to get a few real turns of runway before depletion bites; still a placeholder value, not a tuned one — revisit once there's an actual sense of target game pacing.
* `engine/turn.py` — colonization event resolution pass implemented (2026-07-18): gated on `events.resolve_at_turn <= current_turn` for `event_type='colonize_complete'`, joined against `organizations` and idempotent via the `org_type='ship'` filter (flips to `'colony'` and naturally stops matching). Writes `ship.colonized` directly via SQL rather than `db.events.record_event` — importing it here would create a circular import (`db/events.py` imports `get_current_turn` from this module).
* `db/schema.py` — `resolve_at_turn INTEGER` added to `events` (2026-07-18), plus an index on `(event_type, resolve_at_turn)`.
* `db/events.py` — `record_event()` takes an optional `resolve_at_turn` (2026-07-18). Payload for `colonize_complete` uses `org_id`/`sector_id` (the sector being colonized) rather than `origin_sector_id` as originally sketched here — `origin_sector_id` is a movement/rubber-band concept and doesn't apply to colonization.
* `tests/test_bootstrap.py` — this bullet was stale: the file has been a full suite (idempotency, sector/player/org/pod creation, player_sectors stamping, geometry/sentinel checks) since the 2026-07-22 home-colony work (see below), not a stub. Corrected 2026-07-29.
* **Sector-seeding gap — resolved, and was a misdiagnosis (2026-07-29)** — this bullet had it backwards: pre-seeding only 3 sectors was never a bug. Sectors are meant to be **lazily instantiated** (the canonical model per `docs/data_model_and_storage_design.md`) — a sector row shouldn't exist until a player actually reveals it. `db/sectors.py`'s new `reveal_sector(cur, player_id, x, y, z)` is the single entry point: get-or-create the sector (flat `DEFAULT_SECTOR_RESOURCE_UNITS=20.0` capacities on first creation — randomization deferred), and stamp `player_sectors` visibility. Called from `db/bootstrap.py` (player/colony home-sector placement), `engine/turn.py`'s arrival resolution, and its scan resolution — replacing three near-duplicate manual `player_sectors` upserts. `bootstrap_game()` no longer pre-seeds any sector grid; `config/game_config.yaml`'s `sectors:` block and `config/loader.py`'s `SectorDef` were dead code once nothing read them, and were removed. Knock-on effect: since an unrevealed sector has no row/id, targeting had to become coordinate-based — `preview_move`/`confirm_move` take `dest_x/dest_y/dest_z` instead of `dest_sector_id`, `set_pod_mission`/`set_pod_scan_target` take `target_x/target_y/target_z` instead of `target_sector_id`, and `arrival_queue` stores `dest_x/dest_y/dest_z` instead of an FK. `get_organizations_in_range` now enumerates candidate coordinates mathematically rather than querying existing rows, since most in-range points won't have one yet.

## MCP Tools

* **Space has no negative coordinates (2026-07-29)** — `preview_move`/`confirm_move` now reject any destination with a negative `x`/`y`/`z` (`"Destination coordinates cannot be negative"`), and `get_organizations_in_range`'s candidate enumeration filters them out rather than offering them as targets. Found via a fleet-fan-out simulation where two ships' second-leg jumps landed at negative coordinates — not caught earlier since nothing previously constrained the coordinate space. Scan targeting (`set_pod_mission`/`set_pod_scan_target`) does **not** have this restriction yet — open question whether scanning (observing only, not occupying) should be similarly bounded, or whether the restriction is specifically about where a ship/colony can physically go.
* **`get_organizations_in_range` retired; scan range now actually enforced (2026-07-29, later same day)** — this function never returned organizations at all (it only ever looked up the calling ship's own position), and once we confirmed movement has no range cap (any distance is legal, just costs more transit turns — see the "Movement model" decision below), it had no real remaining purpose for movement. Removed from `navigation_tools.py`/`server.py` entirely. In its place: `get_scan_targets(player_token, org_id)` in `xsettlers_mcp/tools/sector_tools.py`, scoped specifically to scan-target candidates and driven by `get_scan_range(org_id)` (still hardcoded to `1`) instead of a caller-supplied distance — same negative-coordinate filtering as before. Also closed the actual gap this surfaced: scan range was never enforced at resolution (a `# TODO: validate Euclidean range` had sat unfinished in `engine/turn.py`) — a target beyond `get_scan_range()` is now rejected at end-of-turn resolution (not at `set_pod_mission`/`set_pod_scan_target` time — matches the pre-existing documented intent in those functions' own docstrings, a deliberate contrast with movement's reject-before-commit). An out-of-range attempt still pays its food cost but doesn't reveal anything, and logs the previously-unimplemented `alert.scan_out_of_range` event (spec'd in `docs/data_model_and_storage_design.md`, now with `target_x/y/z` instead of the stale `target_sector_id` field name).
* **Immediate in-range feedback when setting a scan target (2026-07-29, later still)** — `set_pod_mission`/`set_pod_scan_target` now compute and return `in_range` (via new `_scan_target_in_range()` in `organization_tools.py`) the moment a scan target is set, and persist it in the pod's `mission_params` alongside the target coordinates. This is advisory, not authoritative: `engine/turn.py`'s resolution still recomputes range fresh against the org's position at that time (which could differ if the org moved in the meantime), so the stored flag is only a snapshot for the player's convenience, letting them notice and fix an out-of-range target before the clock ticks -- if left uncorrected, the food cost still applies with no reveal (see the entry above).
* **Scan targeting workflow settled on direct-entry + validation, not a pick-list (2026-07-29, later still)** — worked out that `get_scan_targets`' candidate list doesn't scale: a future scan range of 3 would balloon it to 123 raw candidates (a sphere's volume grows with the cube of its radius), 94 of which would be physically meaningless anyway since both current scenarios are confined to `z=0`. Decision: the real workflow is direct coordinate entry with immediate legality feedback, not browsing a list. `_scan_target_in_range()` became `_scan_target_status()`, now returning the org's current coordinates plus the computed distance and scan_range alongside `in_range` -- one call gives "you are here, you asked for that, here's whether it's legal," matching the intended interaction. Confirmed two things already work correctly and needed no changes: re-scanning an already-known sector is safe and useful (`reveal_sector` is idempotent -- doesn't re-randomize existing resources -- and always refreshes `player_sectors` confidence, so it's the right tool for noticing depletion or re-checking a decayed view), and rival-organization detection via scan remains explicitly future work (still just a `# TODO` in `engine/turn.py`, not built). **Resolved (2026-07-29, later still):** `get_scan_targets` removed entirely -- from `sector_tools.py`, its MCP tool registration/dispatch in `server.py`, and its tests. Direct-entry + `_scan_target_status()`'s immediate feedback is the whole workflow now; no pick-list helper at all.
* **Pod storage made generic and mission-independent, with cross-pod spillover (2026-07-30)** — found live, during actual play: idling a ship's `produce_energy` pods made their banked energy invisible to consumption, because availability was computed as "whatever's stored on pods *currently* mission'd as produce_energy." The energy wasn't lost, it just stopped being counted the moment those pods were retasked -- which also silently stalled every other pod needing energy that turn (ratio dropped to 0 for anything requiring it, so nothing produced or consumed at all). Root design flaw: storage was implicitly typed by current mission instead of being real, independent inventory. Fixed by replacing `pods.storage_current` with three explicit columns -- `energy_stored`/`food_stored`/`goods_stored` (schema migration in `db/schema.py`, same drop-and-recreate-if-empty pattern as prior migrations) -- so a pod's cargo is tracked directly, independent of what it's currently tasked to do; retasking a pod no longer touches or hides what it already holds. `_available_org_resource`/`_drain_org_resource` in `engine/turn.py` now sum/drain the relevant column across *all* of an org's pods, not just ones on a matching mission. New in the same pass: production overflow no longer just caps and wastes at the producing pod's own capacity -- `_store_org_resource()` fills that pod's own free space first, then spills into any other pod in the org with room (by pod id), and only the remainder is lost if the whole org is completely full everywhere. `db/bootstrap.py`'s full-cargo seeding and `show_organization`/`show_game_status`'s aggregates (`organization_tools.py`) updated to match; the long-dead `energy_consumption`/`food_consumption` pod columns and matching scenario-YAML/config-loader fields were removed in the same pass (fully superseded by `engine/production.py`'s `POD_CONSUMPTION_RECIPE` already).
* **Pod loadout cut from 18 to 6 per ship (2026-07-30)** — a full 20-turn playthrough ended in an exact tie, 14400 points each, with neither fleet ever coming close to depleting or overflowing anything: net drift was only about -60 energy/turn and +100 goods/turn once fleets settled, against a 14400-capacity fleet (18 pods x 100 capacity x 8 ships) -- nowhere near enough movement in 20 turns to create a real scarcity decision. Since total capacity is just `pods_per_ship x 100`, cutting pod count directly cuts capacity by the same factor -- `config/game0.yaml`/`game1.yaml`'s `pods_per_ship` dropped from `count: 6` (x3 missions = 18) to `count: 2` (x3 = 6), keeping the same 1:1:1 energy/goods/food ratio, just scaled down 3x. `tests/test_bootstrap.py`'s pod-count assertions and the `docs/game_instance_mvp.md`/`docs/player_guide.md`/`db/bootstrap.py` references to "18 pods" updated to match.
* **`show_game_status` is now a real fleet report, not just a summary (2026-07-30)** — found live, mid-play: every "show me my fleet" request required hand-written raw SQL, because the tool only returned per-org location/mission/cargo, not tasking, and the aggregate block had no capacity/fullness context. Extended in place (no schema change, no impact on in-progress games): each org entry now includes `tasking` (pod-mission counts, e.g. `{"produce_energy": 2, "produce_food": 2, "produce_goods": 2}`), and the aggregate `assets` block adds `capacity` and `percent_full`. Covers ships and colonies uniformly. New tests in `tests/test_organization.py`; verified against the live in-progress local game (`xsettlers.db`) to confirm the change is purely additive.
* **Status tools canonicalized: civilization status (private) vs. game status (public scoreboard) (2026-07-30, same day)** — the enhanced player-scoped report above got renamed `show_civilization_status` (aliases: "fleet status", "my status") to make room for what "game status" should actually mean: a scoreboard showing *everyone's* standing, not just the caller's own. New `show_game_status(player_token)` returns turn context plus every player's aggregate resource totals (energy/food/goods/total/percent_full), ranked highest-first -- `player_token` only gates *that you're a real player in this game*, not *whose data you see*, a deliberate exception to this module's usual ownership-gating. Decision, confirmed explicitly: aggregate totals are public information anyone can check anytime (matching what `_calculate_final_scores` already reveals at game-over, just available on demand throughout instead of only at the end) -- but fleet composition, position, and tasking of other players stays completely private; the scoreboard exposes only the four aggregate numbers, nothing else. `server.py`'s tool registration/dispatch and `tests/test_gateway.py`/`tests/test_organization.py` updated to match; verified against the live in-progress local game.
* **Presentation hints added to status tools, for non-LLM clients (2026-07-30, same day)** — rationale: most callers of this server are themselves LLM-driven and can format raw JSON fine on their own, but a client with no LLM in the loop (a plain script, a bare bot) would otherwise have to reinvent formatting logic from scratch, and the presentation convention settled on mid-session (short IDs like "P1-01", E/F/G resource shorthand) would only live in one conversation's memory rather than being portable. `organization_tools.py` gained `RESOURCE_ABBREV`, `_short_name()`, and `_tasking_summary()` helpers; `show_civilization_status` now includes precomputed `short_name`/`status`/`tasking_summary` fields on every org (alongside the existing raw fields, which are unchanged) plus a top-level `display` block (`resource_abbrev`, suggested `columns` order); `show_game_status` similarly gained a `rank` field per standing and its own `display` block. Purely additive in both cases -- nothing existing was removed or renamed, verified against the live in-progress local game.
* **`show_civilization_status` gained a per-org `production` breakdown (2026-07-29)** — found live, mid-play: the client was rendering fleet-status tables by hand, picking columns ad hoc each time rather than reading `display.columns` off the response (the whole point of the presentation-hints convention above), and had no way to show a parked ship's actual output without recomputing it client-side from tasking counts. New `_org_production(tasking, in_transit)` in `organization_tools.py` computes gross per-turn output from `POD_PRODUCTION` (energy/food/goods) at full input availability -- explicitly *not* netted against `POD_CONSUMPTION_RECIPE` costs, org upkeep, or storage caps, since replicating `engine/turn.py`'s prorating exactly would mean re-deriving the whole turn-resolution logic; docstring is explicit about this being the nameplate figure, not a prediction. One real-world exception applied: an org in transit is parked at the sentinel sector (0 `energy_capacity`), so its energy production always reads 0 regardless of tasking, matching `engine/turn.py`'s own sector-capacity cap -- food/goods aren't sector-sourced and are unaffected. Each org entry gains `production` (raw dict) and `production_summary` (`_resource_summary()`, same `E:20, F:10` convention as `tasking_summary`); `display.columns` now includes `production_summary`. Purely additive, new tests in `tests/test_organization.py`, verified against the live in-progress local game.
* **Generic hint-driven renderer added: `views/render.py`'s `render_status()` (2026-07-29)** — asked for directly, mid-play: the client had been hand-picking which fields to show from each status tool's JSON, inconsistently, rather than reading the `display` block already returned. Rather than three separate renderers (or hardcoded per-tool formatting), each status tool's `display` block gained `rows_key` (which top-level field holds the row list -- `"standings"`/`"organizations"`/`"tasks"`), joining the existing `columns`/`header`/`resource_abbrev` hints; `render_status()` is a single ~20-line function that reads those hints and renders a markdown table, with zero knowledge of which tool produced the data -- confirmed by a test that feeds it an arbitrary dict shaped the same way and expects it to just work. Also fixed a latent inconsistency this surfaced: `show_civilization_status`'s `columns` referenced raw `cargo` (a nested `{current,capacity}` dict, not a renderable scalar) instead of a precomputed display string -- added `cargo_display` (`"600/600"`, same convention as `show_organization`'s existing `capacity_display`) and pointed `columns` at that instead; raw `cargo` is unchanged. Explicitly an interim/MVP renderer, not the `views/cli_renderer.py`/card architecture sketched in `docs/ui_and_rendering_design.md` (that's still unbuilt) -- this is scoped only to keep local prototyping/play moving. New tests in `tests/test_render.py`.
* **Fleet-status in-transit `status` string simplified (2026-07-29)** — asked for directly, mid-play: `show_civilization_status`'s in-transit `status` string had grown an ETA clause (`", 2 turn(s) remaining (arrives end of turn 8)"` / `", arriving when this turn ends"`) from the earlier "misleading arrival wording" fix below. Dropped, per request -- the string is now just `"in transit -> (x,y,z)"`. `turns_remaining`/`arrival_turn` are unchanged, still real raw fields on the org entry; only the precomputed display string lost the clause. `tests/test_organization.py` updated to match.
* **`show_civilization_status` gained a per-org `storage` breakdown (2026-07-29)** — asked for directly, mid-play: the fleet report only had a combined `cargo` total (current/capacity summed across all resources), no way to see the energy/food/goods split per ship without querying pods directly. Added `storage` (raw `{energy, food, goods}`, same generic-per-pod aggregation as the existing fleet-wide `assets` block, just per-org) and `storage_summary` (via the existing `_resource_summary()` helper, same `E:10, F:20, G:5` convention as `production_summary`); `display.columns` gained `storage_summary`. Purely additive, new test in `tests/test_organization.py`.

## Open Design Questions (resolved)

* **Movement model — resolved (2026-07-29): staying Cartesian/Euclidean for MVP.** Revisited whether `confirm_move`'s free-movement-to-any-coordinate + continuous Euclidean distance should instead be a discrete, direction-constrained model: hexagonal cells within a single plane (6 neighbors), and in full 3D a face-centered-cubic (FCC) lattice whose Voronoi cell is a rhombic dodecahedron (12 neighbors) — stacked hex planes, in effect. Decision: **keep Cartesian/Euclidean for now** — it's already built and tested, and both current scenarios (`game0`/`game1`) are confined to `z=0` anyway, so there's no near-term pressure to change it. Not a dead end: the `sectors` table stores `coord_x/coord_y/coord_z` as plain integers with no Euclidean semantics baked into the schema, and there's no live player data yet, so switching coordinate systems later is a contained rework (mainly `navigation_tools.py`'s distance calc and `get_organizations_in_range`'s neighbor enumeration), not a migration. The bigger change if this is ever revisited is the *mechanic*, not the schema: free jump-to-any-coordinate becomes discrete hop-to-adjacent-cell, which changes the player-facing move flow (name a direction instead of naming a destination) — that's a game-design call, not decided here. If revisited, hex-in-a-single-plane is the natural smaller first step before full 3D FCC, since that's already the shape of both existing scenarios.

## Gateway / Player Onboarding

**Status as of 2026-07-19: built, but deliberately not as originally spec'd.** The MCP Server Layer Design canvas's original design ("gateway.py wraps every tool call with an auth → select-game → bootstrap pre-flight") was revised during implementation — see below for why. This became a real, player-facing flow: a player authenticates against the roster, lists available scenarios, and picks one, which lazily bootstraps that scenario on first selection.

* `xsettlers_mcp/auth.py` — `authenticate(slack_user_id)` implemented. Checks the static roster in `config/game_config.yaml` directly; does **not** depend on the DB or on a game being bootstrapped, since the roster is config-driven and exists before any scenario is chosen.
* `xsettlers_mcp/game_select.py` — implemented: `list_scenarios()` discovers scenarios by scanning `config/game*.yaml` (each scenario file now declares its own `name`/`description` — see `config/game0.yaml`); `get_active_game()` reads the new `games` table; `select_scenario(slack_user_id, scenario_name)` validates against the roster + scenario list, then lazily bootstraps via `bootstrap_game()` if no game is active yet. Rejects switching to a different scenario once one is already active (single shared game per deployed instance for the MVP).
* `config/loader.py` — `load_config()` gained a `scenario_override` param so `select_scenario` can force a specific scenario file instead of the one named in `game_config.yaml`.
* `db/schema.py` / `db/bootstrap.py` — new single-row `games` table (`scenario_name`, `scenario_file`, `selected_by`, `bootstrapped_at`) is the real record of which scenario is active; `bootstrap_game()` now accepts `scenario_file`/`scenario_name`/`selected_by` and writes this row.
* `xsettlers_mcp/server.py` — `list_scenarios`/`select_scenario` added as real MCP tools; `main()` no longer auto-bootstraps at startup (`init_schema()` only — tables, no seeding).
* `engine/turn.py` — `end_of_turn()` now no-ops if the `games` table is empty, so `engine/clock.py`'s clock (which starts ticking immediately at server startup) doesn't silently burn through turns before any scenario has been selected.

### Multi-game lobby — architectural groundwork (anticipated 2026-07-19, not built as a whole; see TODO.md)

The user's longer-term vision: a master lobby where a player authenticates once, sees several available games, picks one, waits for real players to fill in, and NPCs backfill remaining slots. Not built as a whole feature, but the architectural fork was decided early so bootstrap wouldn't need painful rework later, and two small pieces of prep work landed:

* **Decision: one SQLite database per game instance**, not a shared database with a `game_id` column threaded through every table. Rationale: this is already what's built today — `games` is a singleton (`CHECK (id = 1)`), and `select_scenario` already rejects switching scenarios once one is active, i.e. one DB already holds at most one game. A future lobby becomes a thin router pointing a player at the right DB file; it does **not** require touching `organizations`, `pods`, `events`, `arrival_queue`, `player_sectors`, or any query in `engine/turn.py`, `engine/production.py`, or `xsettlers_mcp/tools/*.py`. The rejected alternative (shared DB + `game_id` everywhere) would have meant touching nearly every file built this session — too invasive for "anticipate, don't build."
* `players.is_npc INTEGER DEFAULT 0` added (2026-07-19) — removes a future migration need when NPC fill-in is actually built. Backward-compatible; no existing `INSERT INTO players` call site needed to change.
* `bootstrap_game()` gained a `roster_override` param (2026-07-19) — escape hatch for a future lobby to hand bootstrap a dynamically-assembled roster (real players + NPCs) instead of only ever reading `config/game_config.yaml`'s static list. Not called by anything yet — `xsettlers_mcp/game_select.py`'s `select_scenario()` is unchanged and still always uses the config file's roster.

## NPC strategy profiles — built (2026-07-30)

Scoped first, then built the same day on request. All three gaps identified in the scoping pass were closed:

* **Schema** — `npc_profiles` table (`db/schema.py`): `player_id INTEGER PRIMARY KEY REFERENCES players(id)`, `strategy_name TEXT`, `config TEXT` (JSON), `memory TEXT` (JSON, defaults `'{}'`). One profile per NPC player (1:1, hence `player_id` as the PK rather than a surrogate id) — a plain `CREATE TABLE IF NOT EXISTS`, no migration guard needed since it's a brand-new table.
* **Working memory now lives in the DB** — `npc_profiles.memory`, mutated turn to turn by the strategy function itself and persisted back by `run_npc_decisions()` after each call (same JSON-blob-on-a-row pattern `pods.mission_params` already uses). The prototype's stray `.player2_plan.json` file (confirmed stale — it referenced a previous game's home-sector coordinates) and its script `player2_policy.py` were both deleted — the fan-out logic they contained is ported wholesale into `engine/npc.py`'s `_fan_out_consolidate`, registered as strategy name `"fan_out_consolidate"`.
* **Execution hook** — `engine/turn.py`'s `end_of_turn()` gained a new step 0, *before* step 1 (reset declarations): `run_npc_decisions()` (imported lazily, inside the function body, not at module top — see below). Runs automatically every turn with zero external orchestration; verified end-to-end in `tests/test_npc.py`'s `test_end_of_turn_automatically_drives_npc_through_both_legs`, which calls nothing but `end_of_turn()` in a loop and observes both the opening dispatch and, once the NPC's own ships have actually arrived and `hold_turns` has elapsed, the second-leg jump.
* **Strategy registry** — `engine/npc.py`'s `STRATEGIES = {"fan_out_consolidate": _fan_out_consolidate}`, a `{name: callable}` dispatch table. `run_npc_decisions()` looks up each `is_npc=1` player's `strategy_name` there; an unrecognized name is skipped (not raised) so one bad/renamed profile can't crash the turn for every player.
* **Auth reconciliation** — an NPC is just a player row with `is_npc=1` and a normal `player_token`, so every existing ownership check (`WHERE player_id=?`) works with zero special-casing. `db/npc_profiles.py`'s `assign_npc_profile(player_id, strategy_name, config=None)` sets the flag and upserts the profile row in one call — **dev/test-only, not registered as an MCP tool** (same boundary as the dev-only clock-pause mechanism: NPC assignment is a game-setup/testing concern, not something a player invokes).
* **Circular import, handled**: `engine/npc.py` needs `confirm_move` (from `xsettlers_mcp.tools.navigation_tools`), which itself imports `get_current_turn` from `engine.turn` — so `engine/turn.py` cannot import `engine.npc` at module level without a cycle (`turn → npc → navigation_tools → turn`, the same class of problem `_record_event_direct` already works around for `db/events.py`). Fixed the same way Python code commonly does: the `from engine.npc import run_npc_decisions` import sits inside `end_of_turn()`'s function body, not at the top of `engine/turn.py` — by the time it actually runs (call time, not module-load time), `engine.turn` has already finished initializing, so the cycle never triggers.
* **Transaction safety**: `run_npc_decisions()` is called (and fully completes, including every `confirm_move` call's own commit) *before* `end_of_turn()` opens its own `conn`/`cur` for turn resolution — the existing `conn` used for the earlier "is a scenario selected" check is explicitly closed first. No two connections ever hold overlapping open write transactions against the same SQLite file.
* **Reassigning a strategy resets memory to `{}`** (`db/npc_profiles.py`) — a new strategy has no use for, and can't safely interpret, another strategy's working-state blob.
* Config knobs for `fan_out_consolidate`: `leg_distance` (default 3), `jump_range_per_turn` (default 1), `hold_turns` (default 2). Requires at least 8 of the player's orgs to be ships (2 per direction × 4 directions, same as the original prototype); with fewer, the strategy marks itself done without acting rather than `IndexError`-ing or retrying forever.
* 7 new tests in `tests/test_npc.py` (assignment, reassignment-resets-memory, no-op for non-NPC players, unknown-strategy-is-skipped, the fewer-than-8-ships guard, opening-dispatch, and the full automatic two-leg integration test) plus `npc_profiles` added to `test_schema.py`'s table-existence check. Full suite: 104 passed.

## NPC behavior as data — built (2026-08-11)

Strategies were five Python functions in `engine/npc.py`, each hand-coding a fleet opening. Three of them are now YAML. The goal is a later-phase **NPC builder** that authors strategies without writing code, and the format below is what it will target.

**The line: plans are data, policies are code.** `turtle`, `burst_and_colonize` and `fan_out_consolidate` are fixed openings whose whole sequence is decided in advance — they became `config/npc_programs/*.yaml`. `fan_out` (wait for every scout's scan, then converge the fleet on the richest find) and `frontier_map_stay_frosty` (no terminal state at all) read the world each turn and decide from it; forcing those into `org_command_queue` means conditions, repetition and cross-org coordination — a rule engine inside a command queue — so they stayed as functions. `engine/npc.strategy_names()` is the union, which is what keeps a strategy's *name* a stable contract while its implementation crosses that line: GameHouse validates rosters against it and `run_tournament.py` plays it.

**The ship's log was close but not sufficient**, which is what the work actually was:

* **Action set was `{move, set_pod_task}`** — no colonize, so `burst_and_colonize` was inexpressible. Now `{move, set_pod_task, colonize, aim_scan}`. This needed engine-layer cores to dispatch into, following `apply_confirm_move`'s existing pattern: new `engine/missions.apply_colonize` and `engine/org_scanning.apply_set_org_scan_bearing`, with the tool wrappers (`set_mission`, `set_org_scan_bearing`) becoming thin callers so a queued conversion and a hand-ordered one cannot drift.
* **Circular import, broken first.** `apply_colonize` has to charge the energy, and `_available_org_resource`/`_drain_org_resource` lived in `engine/turn.py` — which imports `engine/ship_log.py`, so anything ship_log dispatches into couldn't reach them (`turn → ship_log → missions → turn`). All three pooled-resource helpers moved verbatim to new `engine/org_resources.py`. Pure move, no behavior change.
* **`record_event_direct` couldn't persist `resolve_at_turn`** — it simply omitted the column, because until now every direct-write caller logged already-resolved facts. `colonize_complete` is scheduled 3 turns out, so the parameter was added.
* **Colonize can legitimately fail at fire time.** A ship may lack the 30 energy when a queued conversion fires even though the order was valid when given. That is not a malformed order, so it gets its own event type (`alert.queued_command_refused`, `db/events.record_command_refused`) rather than joining `alert.queued_command_failed` — folding the two together would bury real defects in a stream of ordinary economic outcomes. First action here that can be *declined* rather than only succeeding or raising.
* **Destinations were absolute**, so a program was pinned to the home sector it was written against. `move` now takes `d_x/d_y/d_z` resolved against the org's position *at fire time* (`engine.ship_log.resolve_destination`) — the same argument that made scan aims offsets so they "survive a move". The negative-coordinate guard had to follow it to fire time, since the origin isn't knowable at queue time. Useful to human players independently: "three further out the way I'm heading" was previously unexpressible.

**The format** (`engine/npc_script.py`). A program is a list of steps; each picks ships and gives them one order, now or on a ship's-log trigger:

```yaml
- ships: {slice: [0, 8], stride: 2, offset: 1}   # 'all', or slice/stride/offset over ships ORDER BY id
  when: after_arrival                            # now | during_transit | before_arrival | after_arrival | {at_turn: N}
  action: move                                   # move | colonize | set_pod_task | aim_scan
  repeat_each: 2                                 # each params entry covers 2 consecutive ships
  params: [{d_x: 0, d_y: 3, d_z: 0}, ...]        # a mapping, or a list cycled round-robin across the selection
```

`params` as a round-robin list is the one idea that removed every strategy's private direction bookkeeping (`directions[i % 4]`, four-entry group dicts) without this layer having to own a compass vocabulary. `repeat_each: 2` is what expresses "two ships per direction", and `stride: 2, offset: 1` picks the second ship of each pair — `fan_out_consolidate`'s two legs, with no code.

**Validation runs at assign time**, not fire time: `validate_program()` is called by `assign_npc_profile()` and refuses to write a profile carrying a malformed program. Same reasoning as `queue_command`'s own up-front param check, one level up — a program is authored by a person, eventually in a UI, and an error has to reach them while they are still looking at it rather than surfacing three turns later inside a clock tick with no one to tell. What is checkable here is structure only; fleet size, positions and energy stocks belong to a game that may not have started. One structural rule worth naming: a `before_arrival`/`after_arrival` step is rejected unless an earlier step sent those ships moving, because arrival-relative orders anchor to a move already under way.

**Equivalence was proved, not assumed.** Each ported strategy scored *identically* to the Python it replaced (`turtle` 2240, `fan_out_consolidate` 2296, `burst_and_colonize` 2582, matching `tourney/summary.json`), and the `events` tables from paired runs — one against a worktree at the prior commit, one against the port — were **byte-identical across all 53 rows**: same orders, same turns, same payloads, same `seq`. Only then were the three functions deleted. That deletion also retired the duplicated-preamble TODO, by removing the duplicates rather than refactoring them.

**Known divergence, recorded deliberately:** `_burst_and_colonize` sized its colonizing cohort as `round(len(ships) * colonize_fraction)`; the program names a fixed `slice: [0, 2]`. Identical at the 8-ship fleets every scenario uses, different elsewhere. Fleet-relative selectors are deferred (see `docs/TODO.md`), and a test asserts the divergence so it cannot become a silent surprise.

Adding a scripted strategy is now adding a file to `config/npc_programs/` — no code change, the same property `config/game<N>.yaml` already has for scenarios. 304 tests pass (up from 267): new `tests/test_npc_script.py`, extended `tests/test_ship_log.py` for the new actions and relative moves, and `tests/test_gamehouse.py` gains an end-to-end check that a roster asking for `burst_and_colonize` by name still seats an NPC that plays under a real `end_of_turn()` loop.
